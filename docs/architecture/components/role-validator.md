# Role: validator

## Purpose
A code-blind judge of evidence. It never sees the diff or tests; it reads the output of the contract
commands the tick ran and marks each assertion pass or fail.

## Where it lives (files)
- Contract: `contracts/validator.md` (schema `validator_result.v1`). Intent: `contracts/intent/validator.jsonl`; `contracts/shown/validator.jsonl`.
- Bundle: `bundles.validator`. Evidence: `ContractJobs.step` (`capsule/contract_jobs.py`) runs `contract_commands` (and the card's `check_cmd` through `capsule/check_gate.py`) when `redesign.check_gate` is on (always for a mac card, whatever the switch: the container cannot test Mac work; with the switch off, a non-mac card's `check_cmd` is not run by the validator) in the strong container. A mac card's (runner tier `mac`, D305: Xcode builds need the host, not the container) own work runs on the host: its `check_cmd`, and any contract command whose first word (after leading `VAR=value` words) is `xcodebuild`, `xcrun`, `swift`, `swiftc`, `codesign`, `simctl` or `plutil`, or that starts with a prefix in the board's optional `mac.host_cmds` list (`mac.host_only`). Those run under the Mac lane profile, no network, in a scratch copy of the clone, inside the lane's one-job lock `mac-lane.lock` (`runners/mac.py` `session`, `contract_jobs._exec_all`). The board's other (Linux) contract commands run in the project container like any card's: same image, same clean checkout, same timeout, and no lane lock. A job with no host command and no blind run never takes the lock. The lock is taken in the job's worker thread when the job starts; if it is busy then, the job goes back for a later pass: no failure, no event, and no job waits for the lane while it holds a pool slot. Host commands written for the worker image (`/trusted`, `/workspace`, `/.gitdirs/<name>`) are mapped to host paths by `mac._host_paths`. Before each container start `StrongRunner._ensure_engine` opens the engine app if `docker info` fails (poll up to 90 s); still down, or a start times out, or fails while `docker info` does not answer (`StrongRunner._engine_gone` raises `EngineDown`), the job records one `contract_infra` event (with the run_id, ending its `contract_started`) and retries within 15 min (the backoff doubles from 60 s), opens one `review_infra` incident at the third failure in a row (and the Z5 docker-down alert fires after `docker_down_s`), with no tick_error and no crash incident. The start-commit re-run (`base_red`) covers container commands only. A dropped job kills its host commands. A lane that cannot run it (switch off, not macOS, no sandbox-exec, no Xcode) holds it with the one `mac_lane_held` reason.
- Rule in code: `capsule/validator_report.py`. Model default Haiku with fallback Sonnet, 8 turns.

## Inputs and outputs
In: the contract and the commands' outputs (tail 8000 characters each, `OUTPUT_TAIL`; per-command timeout 1200 s, `CONTRACT_TIMEOUT`; commands run off the tick thread in `capsule/contract_jobs.py`, and a board may shard a long suite with `contract_shards`, `capsule/shards.py`). Out: `validator_result.v1`: per-assertion results and `not_run` with reasons.

## State it reads and writes
Reads only the bundle. No workspace read.

## Key rules and invariants
With contract outputs present, a validator document may not name anything `not_run` (row 447, `validator_report.py`). A bare `fail` naming no failing item is an invalid document, retried, never a counted round. A `fail` on a plain row whose recorded run exited 0 and ended with a passing test summary (unittest `Ran N tests` then `OK` or `OK (skipped=k)` with k < N, or a pytest `N passed` line) is a skip misread unless the assertion declares a `gap`. The first such document is rejected with an error that names `gap` (`_ok_run_violation`; an `invalid_document` event carries it to the retry, which sees it in `job.json` `inputs.invalid_document_error`, the way `is_repeat` detects a repeat) and retried once: the validator declares the gap or withdraws the fail. If the retry still has that shape, Capsule never passes it and never blocks the card `review_infra`: it records a `validator_error` event (`note_error`) and the fail goes to the implementer as an ordinary review fail, bounded by the round cap. A skip whose reason names another task, plan step or row belongs to that work: the validator judges only the card's own items and, if the card should have made that row live, says so in a note on a passing assertion (`VALIDATOR_OUTPUTS_NOTE`); zero tests, or every test skipped, may still fail (row 459). A `fail` on such a row is valid when the assertion carries a non-empty `gap` (optional `validator_result.v1` string: the acceptance item of this card that the passing output does not prove); it is then a normal validator fail, shown to the implementer with the gap, never retried. Exception: when the row's recorded output is clipped (as long as `OUTPUT_TAIL`), a missing line proves nothing, so a gap fail on that exit-0 row is an invalid document (`_clipped_gap_violation`). It is refused on the retry too (its text has no `OK_RUN`, so `is_repeat` stays false), the validator withdraws the fail (the bundle marks the row CLIPPED), and two refusals take the no-valid-document-twice path: a `review_infra` hold that gets one automatic re-run and then a stall ruling. A review role whose last run ended with no valid document (`invalid_output`) adds one `<role>: no valid document (not counted): <error, first 500 chars>` line to the next implementer brief (`Tick._invalid_lines`); a blind run's error stays withheld (D17: the implementer must not learn the hidden tests) and the failure count does not change. A validator document finally discarded as invalid still gives the next implementer brief its failed assertions' excerpts, as `discarded validator note (not a verdict)` lines in the review findings (`Tick._discarded_notes`). A non-zero `check_cmd` exit, or a missing `check_expect` substring, fails the round on the host whatever the validator says (`check_gate`, behind `redesign.check_gate`). With `redesign.blind_tests` at `report` or `gate`, the validator also gets `blind:<id>` rows (report mode never fails a card; gate mode counts them): see [gate-hidden-tests](gate-hidden-tests.md) and [blind-path](blind-path.md).

Already red? (`capsule/base_red.py`) A failing board contract command, or the card's `check_cmd`, is re-run once on the card's `start_sha` (a real local `clone --shared` checkout from the read-only git dir into the container's tmpfs, same timeout) and its row in `job.json` carries `base: {sha, result, ids}`: `red` (every failing test id of the head also fails there; no parseable ids: both exit codes fail), `different` (it fails with other tests; up to 3 `ids`), `pass` or `unknown` (no start sha, a mac host job, no git or a failed checkout, a re-run timeout). Under a failed validator verdict the failure text then adds "base: `<cmd>` also fails on the start commit <sha12>: pre-existing, not caused by this card" (`red`), "... but with different tests (<ids>): not proven pre-existing" (`different`) or "... passes on the start commit ...: caused by this card" (`check_gate.failures` and `findings`). If every failing command is `red` on the start commit too, one Korin `silent_failure` incident opens per command, key `base-red: <board>: <command slug>`; its text quotes up to 3 failing test ids, else the first failure-like line (warning noise skipped), else the first lines. Pass and fail are unchanged except for one re-run: when the head fails and the start commit passes, the whole command runs once more on the head in the same container. A pass there is `flaky`: the validator gets the re-run row (exit 0) with a note naming the first failing ids, no "caused by this card" line, a `contract_flaky` event, and one `silent_failure` incident per flaky failing test id (up to 3 ids; key `base-flaky: <board>: <id slug>`). A second fail keeps `pass` ("caused by this card"). Known limit: the start-commit run happens in the same container between the two head runs, so a process it leaves alive can affect the head re-run. Nothing is skipped. The merge-gate and flake commands are not re-run.

## Failure modes and what happens
As reviewer: no valid document twice gives `review_infra`.
