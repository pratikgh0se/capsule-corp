# Worker runner, prompt bundles and images

In short:

- **What it is.** The worker is the process that runs one model call for one role on one card.
- **What it does.** It builds the prompt, runs the model, and writes a schema-checked document to the run's spool. The tick starts the implementer's no-network container, and the model sends its shell commands to it.
- **Where the code is.** `capsule/worker.py`, `capsule/runners/`, `capsule/bundles.py` and `docker/`.

## Purpose
Run one model call for one role on one card, in the right sandbox, and turn its output into a
schema-checked document in the run's spool. Provide the workspace the implementer edits and the
container image it runs in.

## Where it lives (files)
- `capsule/worker.py`: `run_one` (`python3 -m capsule run-one`, spawned by `Tick._spawn`). It runs the model (`claude -p`) as a host subprocess and never imports docker. The tick starts the implementer's container (`capsule/tick.py`, then `StrongRunner.start` in `capsule/runners/docker.py`). The model edits its clone with host file tools (`Read,Edit,Write,Glob,Grep`). Its edits are limited to its clone and the run's `requests/` folder; Capsule does not confine its file reads. Every shell command goes into the container through the `mcp__capsule__exec` tool (`capsule/runners/exec_mcp.py`; `StrongRunner.limits` writes its MCP config).
- `capsule/bundles.py`: prompt bundles per role (system prompt = the role's contract, plus the card). `capsule/contracts.py`: parse, lint and render `contracts/*.md`. `capsule/style_lint.py`: output-style check (ASD-STE100).
- `capsule/models/__init__.py`, `claude.py`, `stub.py`: adapters. Only `claude` (the `claude -p` CLI on the host login) is a real runner; `stub` serves tests and golden runs. When the board config selects it with a `reports` list, the worker fills `run_id`, `task_id` and `claim_lock` of each canned report from the current run (`worker._stub_ids`); an entry's own values win. See `docs/architecture/walkthrough.md`. `with_retries` retries only `transient` errors (max 3, exponential backoff).
- `capsule/runners/__init__.py` (tier choice, `reap`), `runners/docker.py` (strong tier), `runners/host.py` (read-only host tier and light tier), `runners/seatbelt.py` (macOS profile renderer; the Mac profile also allows `IOSurfaceRootUserClient`, so a Mac card can render views offscreen), `runners/host_wall.py` (the host wall, D161/D162, an operating-system refusal so a session cannot read the hidden tests: with `redesign.blind_tests` at `report` or `gate`, host sessions start under `sandbox-exec` with a profile that denies file reads of the blind tests, spools and claude project folders; refuses to start if its probe is not refused; see blind-path), `runners/sandbox.py` (runs the lander's suites and the mutation gate inside the board's worker image, never on the host), `runners/exec_mcp.py` (stdio MCP server exposing one `exec` tool that runs shell inside the run's container).
- `capsule/workspace.py`: one git clone per epic, branch and base validation, hardened git calls, `PROTECTED`.
- `capsule/docker_door.py`, `maintenance/events.py`: the one guarded docker door (`docker_run`, `docker_env`). `capsule/docker_argv.py` masks mount sources in a failed docker command before it is stored.
- `docker/base/` (`Dockerfile`, `worker-entrypoint.sh`, `ui-check`, `ui_guard.py`), `docker/stacks/python` and `docker/stacks/web` (each with a `Dockerfile`; web adds `package.json` and `package-lock.json`), `docker/build-base.sh`, `docker/IMAGES.lock` (the maintainer's record of base and stack digests).
- `capsule/image_render.py`, `capsule/image_build.py`, `capsule/paths.py` (`image_record`): the image record (see Key rules).
- `capsule/run_record.py`, `capsule/prior_runs.py`, `capsule/journal.py`, `capsule/checkpoint.py`: per-run start-state record, prior-run paths for reruns, step journal, checkpoint chain.

## Inputs and outputs
In: `spool/<run_id>/job.json` (route, workspace, limits, inputs) and the board DB (read-only). Out:
`requests/` and `report/` documents, `run.json` (exit, tokens, attempts, `error_class`, `session_id`), `worker.log`, `start_state.json`.

## State it reads and writes
Reads the board DB read-only (`connect_ro`). Writes only inside its spool and (implementer) its
workspace. Never writes the board.

## Key rules and invariants
- Tiers: `strong` = hardened Docker container per run (`--network=none`, `--cap-drop ALL`, `no-new-privileges`, tmpfs `/tmp`, `/var/tmp`, `/run`, `--user uid:gid`, `--pids-limit 256`, memory default 5120 MB, git dir mounted outside the workspace); `host` = reviewer, validator, guide, Korin with read-only tools; `light` = seatbelt-sandboxed shell, only with `redesign.light_runner`; `mac` = the Mac lane (`runners/mac.py`): the light profile plus read of the selected Xcode, the Metal GPU client and compiler service, no network by default (per-card `endpoints` only) and no listening socket, `SDKROOT` and the Xcode toolchain dirs on `PATH`, one job at a time host-wide (`mac-lane.lock`), only with `redesign.mac_runner`. A mac card the lane cannot run is held with a `mac_lane_held` reason, never moved to docker or light. A mac card's own work (implementer, `check_cmd`, and host-only commands: an Apple toolchain tool such as `xcodebuild`, or a prefix in the board's `mac.host_cmds`; `host_only` in `runners/mac.py`) runs on the host; the board's Linux contract commands run in the project container like any card's.
- Image record (`runners/docker.py` `worker_image`): the more specific wins (D328): `OPS_WORKER_IMAGE` in the environment, then the board's project row (`capsule-proj-<board>@sha256:...`) in `$CAPSULE_HOME/images.lock`, then `OPS_WORKER_IMAGE` in `ops.env`, then the `capsule-python` row. Nothing recorded means no image and the start refuses (`missing_image_message`); there is no tag fallback. A workspace whose capsule.toml declares a non-empty `[image].stacks` also refuses to start (`MissingImage`, naming the stacks, before any docker call; the card is held as a `capability` block, no failure counted) when no process-environment pin and no project row exist, except stacks exactly `["python"]`; the `capsule-python` fallback serves only undeclared workspaces. The lander's runner has no label (its containers are never reaped as a tick's), but `sandbox.runner_for` sets `image_board` to the landing board, so it resolves the same project row; a missing row there is a landing hold (`needs_docker_tests`, or `blind tests unavailable` for the blind step) naming the stacks and the `image build` remedy, never a docker wait. `redesign.image_loop` is not a switch: `record` is its only value. `python3 -m capsule image render` is a judge (Z2) that turns `capsule.toml [image]` (one stack, apt names, hash-pinned lockfiles, smoke lines) into a project Dockerfile and runs no docker or network; `image build --project DIR --board B` builds it, smoke-tests every `smoke` line in a `--network=none` container, then rewrites only that board's row of `images.lock` (atomic, under a lock); `image which --board B` prints the image the runner would start. Base and stack images are built on the host by `docker/build-base.sh`; workers never build.
- An implementer refuses to run when its workspace is not this epic's clone (`workspace.why_not_worktree`, `error_class: worktree_mismatch`).
- On `max_turns` the implementer gets two more turns to write a checkpoint report, then the chain resumes in a fresh run (`CHECKPOINT_TURNS`, `checkpoint.py`).
- On a fatal exit the tool denials and transcript tail are kept (`_persist_crash_output`).
- `claude -p` flags used: `--output-format json`, `--json-schema`, `--permission-mode dontAsk` (default), `--restricted`, `--strict-mcp-config`, `--max-turns`, `--append-system-prompt`, optional `--fallback-model`, `--effort`.
- Branch and base names are validated before reaching git; git calls use `--end-of-options`; host git pins hooks off.
- Exec tool, strong tier (`runners/exec_mcp.py`, `_WRAP`): each command runs in its own session inside the container (`setsid`, present in every worker image) with stdout and stderr written to files in a container temp dir, not to the `docker exec` pipe, so a process the command leaves behind can never hold the pipe (the `... | tail` hang is bounded by the timeout, not by the orphan). On a normal exit the files are printed back (stdout, then stderr), the command's exit code is kept, and leftovers such as `nohup server &` keep running, so a later exec can use them. Only on a timeout (in-container `timeout` sends TERM) is the command's whole session killed (`kill -KILL -<pgid>`, after listing its processes); the partial output then comes back with one closing line `[exec: timed out after <n>s and was killed; still running at timeout: <ps list>. Tip: ...]`, exit 137, never a silent empty result. A client-side expiry returns exit -1 with the client-side note and whatever the local client captured. The light tier already used its own session and `killpg` and is unchanged.

## Failure modes and what happens
Rate limit: the adapter returns `error_class: rate_limit` with `retry_after`; the tick pauses the account. Timeouts: the tick kills the process group after `max_runtime_seconds`. Orphan containers are reaped each pass. A container start that times out, or fails while `docker info` does not answer, raises `EngineDown` (retried with backoff, no crash incident; the text names the `open -a` exit and the last `docker info` error, and a worker start that times out on a live engine backs its card off 60 s doubling to 900 s, one `review_infra` incident on the third in a row); a `docker info` where every probe of the 90 s wake wait timed out (a hung OrbStack) gets `orb stop` then `orb start` under a host-wide lock, at most 6 per rolling day and one per hour (`RESTARTS_PER_DAY`, `RESTART_GAP_S` in `runners/docker.py`; stamps in `$CAPSULE_HOME/engine-restarts.json`), never while the keeper lands, with one `engine_restarted` board event; a start that times out on a live engine records `start_slow`; a start docker refuses with the engine up is a visible card failure.

## Docker engine switch
- The engine is chosen by `maintenance/lib_docker_engine.sh`: env `CAPSULE_DOCKER_ENGINE`, else the one-line file `$STATE_DIR/docker-engine`, else `orbstack` (the default). `desktop` selects Docker Desktop. An unknown value exits 2.
- The script sets `DOCKER_ENGINE` and `DOCKER_ENGINE_{BIN,CONTEXT,TITLE,APP,APP_PATH,OPEN_HINT,CASK}` and puts that engine's `docker` first on `PATH`. deploy.sh (maintainer only, not in the public edition) and `bin/hoi-poi.sh` source it, so their "start the engine" messages name the engine you chose.
- The hung-engine hard restart (`capsule/docker_door.py`) is skipped when the engine is not OrbStack.
